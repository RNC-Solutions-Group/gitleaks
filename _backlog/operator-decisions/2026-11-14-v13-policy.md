## Implementation interpretation and acceptance requirements

### OP-01 — Report-only keyed HMAC grouping: approved direction

- Build a separate, explicitly enabled grouped-report/sidecar capability; never drop, merge, or silently suppress primary findings, commits, fingerprints or exit codes.
- Derive scoped grouping identifiers with keyed HMAC-SHA-256 using a dedicated domain separator. **Do not** use bare SHA-256 or expose an enumerable unkeyed digest of secret content.
- Define the canonical grouping input and scope; decide how behavior differs for repeated values across different rules, file locations, commits, case/whitespace and redacted findings.
- The caller must explicitly provide a protected key by an approved mechanism; reject missing/invalid keys in grouping mode rather than falling back to plaintext or unkeyed hashing. Never persist key material in Git, reports, arguments visible in logs, diagnostics, profiling or telemetry.
- Explicitly document cross-run determinism and key rotation: grouped IDs cannot remain stable across independent keys by accident. Test using synthetic secrets, including low-entropy values, output redaction, empty/invalid keys, multiple finding locations, and scan failures.
- The choice of key-delivery method, scope and output schema must receive technical review before final integration. This operator approval does not waive security gates.

### OP-02 — Go module identity: decision reopened, not settled

- Compare at least: (A) retain \`github.com/zricethezav/gitleaks/v8\` with RNC GitHub releases/binaries/images; (B) adopt an RNC-owned \`/v8\` module identity; (C) maintain a documented compatibility/distribution strategy if practical.
- Verify actual \`go build\`, \`go test\`, \`go install\`, \`go get\`, \`go run\`, dependency/import behavior, internal package paths, generator, GoReleaser/linker version stamping, Go proxy/module case rules and potential fork/repository naming differences.
- Cover effects on existing downstream importers and reproducible builds; distinguish the GitHub repository name, Go module path, binary product name, Git tag, and container identity.
- Produce an evidence-based course-of-action comparison with migration costs, compatibility breaks and recommended selection. **No \`go.mod\` rename, broad import rewrite, new tag or published artifact without subsequent explicit operator authorization.**
- Preserve the previously settled repository name \`gitleaks\` and release branch \`rnc-mod\` unless separately directed.

### OP-03 — First-parent default: comparative evidence, no automatic switch

- Run the existing normal and hostile/evil merge fixtures, first-parent opt-in and candidate alternatives against identical pinned source/config; include merge-only secrets, normal merges, conflict resolutions, octopus merges and changed-path scope.
- Quantify coverage changes, duplicate findings, re-reporting, fingerprints, ignore/baseline compatibility, source coordinates, report schemas and Git-version requirements; distinguish new true findings from duplicates.
- Preserve fail-closed rejection of unsupported combined/remerge formats. No silent path/commit rewrite, no falsified clean-scan coverage claim.
- Recommend whether first-parent should become the default, remain opt-in or be exposed through a separate comprehensive-history preset, with a migration and compatibility plan.
- **Do not change default history flags in this checkpoint.** The operator has authorized evaluation, not adoption.

### OP-04 — Local config versus CI trust: accepted behavior

- Preserve ordinary source-local config discovery for backwards compatibility.
- Publish safe CI invocation examples that explicitly select a controlled, trusted config outside the untrusted scan target and use \`--no-local-config\` to block incidental source-local discovery. Verify the exact CLI precedence: an explicit \`--config\` still takes precedence.
- Assess the distinct trust boundaries for \`GITLEAKS_CONFIG\`, \`GITLEAKS_CONFIG_TOML\`, \`.gitleaksignore\`, baseline inputs and local templates; document how CI prevents untrusted repository contents from choosing these inputs.
- A trusted policy must not be silently superseded by a checked-out target. Test with an attacker-controlled \`.gitleaks.toml\` designed to disable rules using only synthetic data.
- Do not globally change the default to fail closed on local config; a future secure-by-default migration needs separate approval.

### OP-05 — Opt-in strict configuration validation: implementation authorized

- Design a flag or config-verification mode (provisional CLI name \`--strict-config\`) that **rejects** unknown/misspelled fields and mis-scoped or unsupported TOML constructs with actionable file/table/field diagnostics.
- Validate extension-chain configs and pre-existing aliases/deprecations explicitly; compare valid default and custom configs under standard and \`gore2regex\` builds.
- Preserve ordinary non-strict parsing behavior, rule counts, matching, allowlists and scanning exit semantics when strict mode is disabled.
- Strict-mode validation failures must produce a nonzero operational error before returning clean scan results or writing reports.
- Avoid echoing sensitive configuration values and patterns in diagnostics. Add negative tests for nested unknown fields, typos, empty rules, malformed TOML, extension precedence and unsupported \`minVersion\` cases.
- Implement and test on a separate work branch; do not merge without review.

### OP-06 — Fingerprint v2: architecture only, with explicit v1 migration

- Design a versioned, content-discriminating ignore fingerprint that does not expose raw/unencrypted secret material or a dictionary-attackable unkeyed digest; assess whether a caller-held key is appropriate and coordinate with, but do not conflate with, OP-01 HMAC grouping.
- Retain unchanged v1 fingerprints, default scan output, current ignore-file support, baselines and existing integrations unless a separately selected mode is active.
- Compare a dual-acceptance migration mode (v1 + v2) with a v2-only enforcement mode. **Do not claim that dual acceptance prevents a legacy v1 entry from suppressing a different secret at the same location.**
- Specify version prefix, canonicalization, key provision/rotation, cross-platform path and CRLF invariants, redaction, determinism, report/export schema impacts, and compatibility with old \`.gitleaksignore\` entries.
- Compare upstream PRs #2286 and #1566 as designs, not automatically adopted source. Deliver exact fixture matrix, risks, migration strategy and recommended policy; **no implementation or activation pending further operator decision**.
